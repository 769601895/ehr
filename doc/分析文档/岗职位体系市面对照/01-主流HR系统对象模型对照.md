# 主流 HR 系统：职务 / 职位 / 岗位 对象模型对照

> 目的：从市面产品**抽公共骨架**，避免被各厂商中文标签带偏；并对照本 EHR（`DutyId` / `PostId` / `CcCode`）。  
> 口径日期：2026-03；依据公开文档与产品说明（非实施配置实勘）。

---

## 1. 先统一「语义层」（再看厂商名词）

各厂商中文「岗位 / 职位 / 职务」**互不相同**。对照时只用下面 6 个语义槽：

| 语义槽 | 含义 | 英文常见名 |
|--------|------|------------|
| **S1 组织单元** | 公司/部门/成本中心/监管组织 | Org / Department / Supervisory Org |
| **S2 标准工作定义** | 因事而设的工作类型、JD、默认薪级/职级 | Job / Job Profile / Job Classification / 基准岗位 |
| **S3 组织下可占坑** | 挂在某组织上的编制座位，可空缺 | Position / 职位（坑位义） |
| **S4 层级头衔/管理级** | 权责层级称呼或管理级别 | Management Level / Job Level / 职务 |
| **S5 职级带宽** | 薪酬与发展标尺 | Grade / Pay Grade / 职级·职等 |
| **S6 任职关系** | 人占用坑/岗的时间段记录 | Assignment / Job Info / 任职 |

```text
S1 组织 ──挂──► S3 坑位 ──引用──► S2 标准岗
                    │                 │
                    │                 ├──可选──► S5 职级
                    │                 └──可选──► S4 职务/管理级
                    └──被──► S6 任职 ◄── 员工
```

**黄金法则：** 统计「编制空缺」看 **S3**；统计「岗位族/能力标准」看 **S2**；名片 Title / 任免看 **S4**；薪资带宽看 **S5**。

## 3. 分厂商：怎么「搭」的（结构摘要）

### 3.1 国际三大（语义最清晰）

| | Workday | SuccessFactors | Oracle HCM |
|--|---------|----------------|------------|
| 标准岗 | Job Profile | Job Classification | Job |
| 分组 | Family → Family Group | Job Function 等 | Job Family / Subfamily；Job Set 分区 |
| 坑位 | Position（可选 JM 不建坑） | Position（可多人、父子位） | Position（部门下；可职位树） |
| 人 | 占 Position 或 Job | Job Info 同步 Position/Job | Assignment |
| Title | Business Title ≠ Profile | Job Title 可从 Classification 传播 | Job/Position 结构属性 |
| 组织 | 监管组织决定 PM/JM | FO 组织对象 + Position Org Chart | 部门 + 可选 Position Hierarchy |

共同点：**标准岗与坑位分离**；人通过任职占坑（或弱化为 Job Management）；职级/薪级挂标准岗或坑。

### 3.2 北森

- **多维组织**并行：行政 / 业务 / 成本 / 项目 / 虚拟。  
- **岗职务体系**：岗位、职务、职级、序列、任职资格一体，服务晋升与盘点。  
- **编制 3.x**：控到组织，并可按职务、职位、职级、序列、用工形式等组合；流程卡招聘/Offer/调动。  
- 特点：**编制维度极强**；「职位」更多是控编与任职维度，不一定强制「一坑一人」欧美 Position。

### 3.3 用友 YonBIP

典型搭建顺序：

1. 行政组织 + 人力资源组织（共享中心可与行政树分离）  
2. **职务体系**：职等 ←→ 职级；职务类别 → 职务  
3. **岗位体系**：岗位序列 → **基准岗位** → 各部门 **岗位**（可按职务+部门或基准岗+部门批量生成）  
4. 组织**版本化**调整时联动岗位与任职  

注意：用友语境里「岗位」常已是 **组织下实例（偏 S3）**，「基准岗位」才是 **S2**；「职务」是独立体系（偏 S4+S5 绑定）。

### 3.4 飞书 / 钉钉

| | 飞书人事 | 钉钉智能人事 |
|--|----------|--------------|
| 岗职 | 职务、职级、序列、职等、岗位（开放平台「岗职」域） | 职位 / 职级 / 职务 **三套列表 API** |
| 任职 | 雇佣 + 任职记录；异动含职位变动 | 调岗改部门+职务+职位+职级 |
| 编制 | 编制规划资源 | 弱 |
| 定位 | 中大型 CoreHR 方向 | 协同办公花名册增强 |

### 3.5 金蝶 / i人事（归纳）

- 金蝶：强调多形态组织、多职位体系、岗位差异化、汇报关系多类型。  
- i人事等：宣传「组织树 / 岗位树 / 人员」；岗位常同时承担标准与占编；适合中大型快速落地。

## 6. 三种市面主流「构建范式」

### 范式 A — 国际 CoreHR（WD / SF / Oracle）

```text
Org → Position(坑) → Job(标准) → Grade
              ↑
           Assignment(人)
```

- 适合：编制严、空缺可视、全球汇报与继任。  
- 代价：实施重，一线高流动部门常用 Job Management 降级。

### 范式 B — 国产集团岗职 + 多维编制（北森 / 用友旗舰）

```text
多维Org + 职务体系 + 基准岗/岗位库
         ↓
   编制方案(多维度) ←→ 招聘/异动
         ↓
      任职记录(人)
```

- 适合：集团多法人、共享服务、按职级/序列控高P人数。  
- 坑位可「逻辑存在」（编制行）而不建物理 Position 表。

### 范式 C — 协同花名册增强（钉钉 / 轻量飞书用法）

```text
部门树 + 员工字段(职位/职务/职级)
```

- 适合：中小、先有协作后有 HR。  
- 代价：难做真编制闭环与岗职标准治理。

**本 EHR 当前更接近：范式 C 向「B 的简化版」过渡**——已有独立 `hr_post` + `DutyId`，但无 S3 坑位、无完整职级主数据、编制未与招聘闭环。

## 7. 与本系统落地建议（对照结论）

| 层级 | 建议 | 对应现状 |
|------|------|----------|
| 必保 | S1 组织 + S2 岗位（`hr_post`）+ S4 职务 | 已有 |
| 短期增强 | S5 职级（或复用代码类）挂岗位默认级；岗位说明书/族 | 部分缺 |
| 中期 | S3 职位坑 **或** 「部门×岗位编制行」二选一 | 未建 |
| 任职 | S6 任职时间轴（主兼岗）；异动写任职而非只改主档三字段 | 异动有，任职模型可加强 |
| 原则 | 对内文档统一用 S1–S6；界面文案再映射中文 | 避免再混用 |

**若只要一张选型卡：**

| 企业诉求 | 更接近哪家范式 | 本系统优先补 |
|----------|----------------|--------------|
| 要空缺率、一坑一招 | 范式 A | 职位/开缺 |
| 要集团按职级/序列控编 | 范式 B | 编制维度 + 岗职级 |
| 要快速花名册+调岗 | 范式 C | 维持直挂，治理码表 |
