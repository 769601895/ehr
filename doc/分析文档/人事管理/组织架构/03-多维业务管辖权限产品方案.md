# 多维业务管辖权限产品方案

> 日期：2026-11-05  
> 角色：HR 产品方案（市面通用做法 + 本产品落地建议）  
> 关联：[`01-user-cc-scope.md`](./migration-plan/design/01-user-cc-scope.md)、[`02-人员模块按管辖过滤改造方案.md`](./02-人员模块按管辖过滤改造方案.md)  
> 范围：人事 / 考勤 / 薪酬等模块的「谁能管哪些人」——与菜单功能权限分离

---

## 1. 结论先说

市面成熟 HR（SAP SuccessFactors、Workday、Oracle HCM、北森、薪人薪事、用友/金蝶人力云等）几乎都把「管辖」拆成两层，而不是一套「部门管辖」打天下：

| 层 | 回答的问题 | 典型载体 |
|----|------------|----------|
| **组织归属（Organization）** | 这个人「挂」在哪：行政组织、成本中心、发薪主体、考勤点 | 员工主档上的多字段 / 多关系 |
| **业务管辖（Responsibility / Data Scope）** | 这个操作员在某业务域「能看见、能处理」哪些人 | 按**业务域**配置的数据范围规则 |

关键产品原则：

1. **员工可以有多个「业务归属」**（行政部门 ≠ 发薪主体 ≠ 考勤组织），彼此独立维护。  
2. **操作员管辖按业务域拆开**（人事管辖、考勤管辖、薪酬管辖可不同）。  
3. **同一业务域内可再按员工分群**（用工类型、薪资组、职级、厂别、成本中心等），支持「张三管一类、李四管一类」。  
4. **列表过滤维度 = 该模块认定的「业务主归属」∩ 操作员在该域的管辖规则**，禁止一律用行政 `cc_code` 过滤所有模块。

对本产品：`Usercc`（部门管辖）是**人事域的默认底座**；考勤/薪酬应在此之上扩展「业务域管辖」，而不是把所有模块硬绑到同一棵行政树上。

## 2. 市面怎么做（归纳）

### 2.1 三种主流模型

| 模型 | 做法 | 适合 | 局限 |
|------|------|------|------|
| **A. 单一组织树 + 含下级** | 账号挂若干组织节点，全模块共用 | 单法人、组织=考勤=发薪 | 算薪在 A、考勤在 B 时立刻失效 |
| **B. 多组织类型 + 分域范围** | 员工挂多组织关系；权限按「安全组织 / 业务单元」分模块配置 | 集团、多厂、共享服务中心 | 配置略重，需产品叙事清晰 |
| **C. 角色职责包（Responsibility）** | 给用户绑「职责」：业务功能 + 数据安全配置档（组织/人员组） | Workday / Oracle 风格 | 抽象度高，实施依赖顾问 |

**通用结论**：中大型、多法人、共享 SSC 几乎都走向 **B 或 C**；纯中小单厂可先 A，但产品架构要预留 B。

### 2.2 「人」本身的多归属（与权限正交）

成熟产品在员工主档（或关系表）上至少区分：

| 归属类型 | 用途 | 谁维护 |
|----------|------|--------|
| **行政/编制组织** | 组织人数、编制、人事档案主挂靠 | 人事 |
| **发薪主体 / 公司** | 工资核算公司、个税、社保主体 | 薪酬 / 人事 |
| **考勤组织 / 考勤点** | 班次、打卡点、异常处理责任 | 考勤 |
| **成本中心** | 费用归集（可与行政不同） | 财务协同 |
| **直线经理 / HRBP** | 审批、辅导、部分可见范围 | 组织/人事 |

跨公司场景的正确建模是：**改「业务归属字段/关系」**，不是让一个人只能属于一个部门却用管辖硬拗。

> 例：行政挂 B 厂品保部，发薪主体 = A 公司，考勤组织 = B 厂产线 → 三套字段/关系并存；各模块按自己的字段做范围过滤。

### 2.3 「操作员」的分域管辖

| 业务域 | 常见过滤锚点 | 典型再细分 |
|--------|--------------|------------|
| **人事 Personnel** | 行政组织树 + 是否含下级 | 员工状态、用工类型、HRBP 负责单元 |
| **考勤 Time** | 考勤组织 / 考勤组 / 厂区 | 班制、车间、考勤员分区 |
| **薪酬 Payroll** | 发薪主体 + **薪资组 / 工资核算范围** | 计时/计件、干部/工人、外包、职级段 |
| **招聘 / 培训等** | 各自业务组织或岗位族 | 按需 |

同一人在不同模块看到的员工集合**可以不同**——这是特性，不是缺陷。

### 2.4 「一类员工一个负责人」怎么配

市面不靠「再挂一套行政树」，而靠 **人员分群（Population / Security Group / 权限条件）**：

```text
操作员薪酬管辖 =
  (发薪主体 ∈ {A公司, C公司})
  AND (薪资组 ∈ {干部月薪, 职员})
  AND (可选：行政组织 ∈ 某子树，作二次收窄)
```

配置形态常见三种：

1. **静态名单组**（适合小范围特殊人员）  
2. **动态规则组**（按字段条件自动入组，推荐主路径）  
3. **职责包模板**（「华南计时工考勤员」预置规则，批量赋给用户）

张三 / 李四分管不同类型员工：各自绑不同「薪资组 + 发薪主体」规则即可，**不必拆两套组织树**。

## 3. 场景拆解（产品语义）

### 3.1 算薪在 A，考勤在 B

| 对象 | 应怎么记 | 过滤谁看得到 |
|------|----------|--------------|
| 员工 | `PayCompany=A`，`AttendOrg=B…`，行政组织可仍为 B 或另有编制部门 | — |
| 考勤员 | 考勤域管辖含 B 相关考勤组织 | 只在考勤模块看见此人 |
| 薪酬专员 | 薪酬域管辖含 A + 对应薪资组 | 只在薪酬模块看见此人 |
| 人事专员 | 人事域按行政组织 | 人事列表按行政树；可不出现在对方考勤/薪酬列表（若未授对应域） |

**禁止**：用「把人调到 A 部门」来迁就发薪，导致编制、考勤、编制报表全部失真。

### 3.2 薪酬多人分管不同类型员工

| 操作员 | 薪酬域规则示例 |
|--------|----------------|
| 张三 | 发薪主体=集团制造业 ∪ 薪资组∈{计时工, 计件工} |
| 李四 | 发薪主体=集团制造业 ∪ 薪资组∈{职员, 干部} |
| 王五（共享中心主管） | 发薪主体=全部 ∪ 特权或并集查看（只读） |

人事域仍可按部门管辖；**薪酬列表默认不套人事部门树，而套薪资组/发薪主体**（可用部门作辅助筛选，但是否参与权限由产品开关决定）。

### 3.3 管辖类 vs 员工类业务（与公司参数规则对齐）

| 场景类型 | 数据范围用谁的组织 | 公司参数解析 |
|----------|-------------------|--------------|
| **管辖类**（代办列表、按管辖筛数、专员作业池） | 操作员业务域管辖 | 选手动部门 / 管辖同属一公司兜底 |
| **员工类**（入职落档、算薪、考勤日结落在具体人） | 以**该员工**对应业务归属为准 | 按员工本人部门/发薪主体解析，禁止误用操作人管辖部门 |

管辖解决「谁能进池子」；落账规则解决「这笔业务跟哪家公司参数走」——二者不可混为一谈。

## 4. 推荐目标架构（本产品）

### 4.1 概念模型

```text
┌─────────────────────────────────────────────────────────┐
│ 菜单/按钮权限（SysRole / API）—— 能不能进功能            │
└─────────────────────────────────────────────────────────┘
                            ×
┌─────────────────────────────────────────────────────────┐
│ 业务域数据范围（本方案）—— 能看见/处理哪些人              │
│  Domain ∈ { Personnel, Attendance, Payroll, … }         │
│  Rule = 组织范围 ∪ 人员分群条件（可组合）                 │
└─────────────────────────────────────────────────────────┘
                            ×
┌─────────────────────────────────────────────────────────┐
│ 员工多归属主数据                                         │
│  行政 cc_code / 发薪主体 SiteCode / 考勤组织 / 薪资组…   │
└─────────────────────────────────────────────────────────┘
```

求交结果才是模块列表可见集。超管 / 「全部数据」角色可跳过数据范围层。

### 4.2 员工多归属（主数据，P0 起逐步补齐）

在员工主档或关系表明确字段（名称可按现有库调整）：

| 字段建议 | 说明 | 模块默认锚点 |
|----------|------|--------------|
| `CcCode` | 行政/编制部门（已有） | 人事 |
| `PaySiteCode` / 发薪主体 | 与 `HrCompanyParam.SiteCode` 对齐 | 薪酬、社保 |
| `AttendCcCode` 或考勤组 | 可与行政不同；无则回退 `CcCode` | 考勤 |
| `PayGroup` 薪资组 | 分管类型员工的主轴 | 薪酬 |
| 成本中心等 | 按财务需要 | 报表 |

维护入口：人事调岗可联动提示「是否同步考勤组织/发薪主体」，但**默认不强制三合一**（产品可做公司参数开关）。

### 4.3 业务域管辖配置（权限，相对 Usercc 的扩展）

**阶段定位**：

| 阶段 | 能力 | 说明 |
|------|------|------|
| **现有 / 近期** | `Usercc` 部门管辖 | 作为 **Personnel 域** 的组织范围；考勤/薪酬可临时「继承人事」或「暂不控」需显式声明 |
| **目标** | `UserBizScope`（名可再定） | 按 Domain 配置：组织锚点类型 + 根节点 + 含下级 + 可选人员分群条件 |

建议表意（设计级，非最终 DDL）：

```text
UserBizScope
  UserId
  Domain          -- Personnel | Attendance | Payroll
  OrgAnchorType   -- AdminCc | AttendCc | PaySite | …
  CcOrSiteCode    -- 根编码（部门或厂别）
  IncludeChild
  PopulationId    -- 可空；人员分群（动态规则）

Population / PopulationRule
  条件：PayGroup IN (…) ; EmpType IN (…) ; Grade BETWEEN … 等
```

解析 API 统一封装（禁止各模块自抄）：

| 方法 | 语义 |
|------|------|
| `ApplyEmpScope(domain, query)` | 按该域规则过滤员工 |
| `EnsureEmpInScope(domain, empId)` | 写操作越权 |
| `ResolveEmpBusinessKeys(emp)` | 取员工发薪主体/考勤组织等供业务落账 |

与 [`02`](./02-人员模块按管辖过滤改造方案.md) 关系：02 的 `HrUserCcScopeService` = **Personnel 域** 的第一实现；本方案要求后续模块**不要**直接复用「行政树」冒充考勤/薪酬范围，而应调用带 `domain` 的统一入口（初期 Attendance/Payroll 可配置为 `InheritPersonnel`）。

### 4.4 各模块默认过滤策略

| 模块 | 可见员工条件（推荐默认） | 组织树 UI |
|------|--------------------------|-----------|
| 人员资料 / 异动 / 合同等人事 | `行政 CcCode` ∈ Personnel 组织范围 ∧ 分群（若有） | 行政森林根（同 02） |
| 排班 / 异常 / 请假代办（考勤作业） | `考勤组织` ∈ Attendance 范围 ∧ 分群 | 考勤组织树；无独立树则行政树但过滤锚点仍是考勤组织 |
| 薪资档案 / 算薪 / 个税（薪酬作业） | `发薪主体` ∈ Payroll 厂别范围 ∧ `薪资组` 等分群 | 常按公司/薪资组筛选，而非行政深树 |
| 仅查询报表 | 可单独「报表域」或按报表类型选锚点 | 避免超管报表被作业管辖误伤时可设只读宽范围角色 |

### 4.5 与框架 DataScope / ExtOrg

- Sys* 继续走框架机构 DataScope。  
- HR 业务**不以** `SysOrg` Id 列表展开过滤（与 01/02 一致）。  
- 账号页长期应能维护「分域管辖」；短期 Personnel 走 Usercc，其它域可「继承」并在界面注明。

## 5. 配置叙事（给实施与管理员）

建议账号/权限中心呈现为三块，避免一个「管辖部门」包打天下：

1. **功能权限**：角色菜单与按钮。  
2. **人事数据范围**：管辖行政部门（Usercc）。  
3. **业务数据范围（进阶）**：考勤组织范围、薪酬（发薪主体 + 人员分群）。

帮助文案要点：

- 「管辖」只决定作业池；员工算哪家工资看**发薪主体**。  
- 跨厂考勤/发薪：请改员工归属，不要靠扩大管辖「借人」。  
- 同一模块多人分管：用人员分群（薪资组/用工类型），不要复制整棵组织树。

## 6. 分期建议

| 期 | 内容 | 验收要点 |
|----|------|----------|
| **P0** | 落地 Personnel=`Usercc`（见 02）；员工主档梳理发薪主体/考勤组织字段缺口清单 | 人事树/列表按管辖；超管全量 |
| **P1** | 明确员工「发薪主体」「考勤组织」维护与回退规则；考勤/薪酬模块开关：`InheritPersonnel` / `OwnDomain` | 文档+配置可讲清 3.1 场景 |
| **P2** | `UserBizScope` + 动态人员分群；薪酬按发薪主体×薪资组分管 | 张三/李四分管两类人互不可见作业数据 |
| **P3** | 职责包模板、共享服务中心只读并集、审批人范围与作业范围分离 | SSC 场景可实施 |

**非目标（本期不写进范围）**：用一套行政管辖自动推导所有模块；离职回收工号式的「权限回收」与数据范围混谈；把 Population 做成任意 SQL（须白名单字段）。

## 7. 多语言

- 域名称、空范围提示、配置页标签：UI i18n（zh-CN / zh-TW / en / th / vi）。  
- 薪资组、组织名称等业务显示名：走既有译文机制；权限配置存 **Code**，不存译文。

---

## 8. 风险与产品红线

| 红线 | 原因 |
|------|------|
| 全模块只用行政 `CcCode` 过滤 | 无法支撑算薪 A / 考勤 B |
| 展开部门 Id 百万行进缓存 | 组织规模下不可用（01 已禁） |
| 管辖与公司参数解析混用操作人部门处理员工落账 | 违反公司参数/工号规则 |
| 静默「继承人事」却不告知实施 | 现场按单一管辖配置，跨域场景必翻车 |
| 人员分群无审计 | 算薪可见性纠纷无法追溯 |

---

## 9. 对本仓库的落地取舍（产品决策建议）

1. **承认多维**：组织归属 ≠ 业务管辖；业务管辖再按 Domain 拆分。  
2. **P0 只把人事做对**（02 + Usercc），同时在主数据上**预留/补齐**发薪主体、考勤组织、薪资组。  
3. **考勤/薪酬默认策略写进方案**：上线前二选一——暂继承人事（明确技术债）或按自身锚点过滤。  
4. **分管类型员工**走 Population，不走第二套行政树。  
5. **统一 Scope 服务带 Domain**，避免各模块复制前缀 SQL。
