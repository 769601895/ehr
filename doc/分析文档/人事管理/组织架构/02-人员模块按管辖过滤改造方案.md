# 人员模块按管辖过滤改造方案

> 日期：2026-11-05  
> 背景：账号 `adm` 在「账号管理」配置了管辖「管理部」「品保部」，打开「人员资料管理」左侧部门树仍是整个「集团」。  
> 关联：[`migration-plan/design/01-user-cc-scope.md`](./migration-plan/design/01-user-cc-scope.md)（Usercc 目标设计）

---

## 1. 现象与结论

| 项 | 现状 |
|----|------|
| 账号管理「管辖部门」 | 写入框架表 `SysUserExtOrg`（`OrgId` → `SysOrg`），界面文案为管辖部门 |
| 人员资料左侧树 | `orgTree.vue` → `getHrOrgList` → `HrOrgService.GetList`，读全量 `cc_mstr` **无用户范围过滤** |
| 人员列表 | `HrEmpService.Page` 仅按所选 `parentCcCode` / 关键字过滤，**无管辖约束** |
| 目标设计 | 人事数据范围应走 `Usercc(UserId, CcCode, IncludeChild)` + 当前 `cc_level` 前缀（见 01 设计稿） |
| 落差 | **Usercc 未落地**；账号 ExtOrg **未接到**人事组织/员工查询 |

**结论**：不是「配置丢了」，而是 **HR 读路径从未按管辖裁剪**；账号侧管辖与人事侧组织是两套模型，中间缺桥。

另：若登录身份实际为超管（界面水印常见「超级管理员」），框架侧本就会放行全机构。验收时须用**非超管**账号登录验证。

---

## 2. 根因链路

```text
账号管理保存
  → SysUserExtOrg(UserId, OrgId) + 用户主 OrgId
  → 框架 GetUserOrgIdList / DataScope（主要服务 Sys* 模块）

人员资料打开
  → HrOrg.GetList / HrEmp.Page
  → 只查 cc_mstr / h_emp_mstr
  → ✕ 不读 ExtOrg，不读 Usercc
  → 整棵集团树 + 可点根看全员
```

已有局部桥接（仅公司参数兜底）：`HrCompanySiteResolveService` 会把当前用户 `OrgId`/`OrgIds` → `SysOrg.Code`，且约定 **Code 与 `cc_mstr.cc_code` 对齐** 时才有效。人员树/列表**未复用**该语义做范围过滤。

---

## 3. 目标行为（产品）

对非特权用户：

1. **部门树**：只展示「管辖根 +（默认）其下级」拼成的森林；人数只统计可见范围内员工。  
2. **员工列表**：无论是否点树，结果集员工所属部门必须落在管辖范围内；越权 `ccCode` 参数服务端拒绝或忽略。  
3. **含下级**：与设计稿一致，默认 `IncludeChild=1`，用**当前** `cc_level` 前缀匹配（组织调动不改授权行）。  
4. **特权**：超管 / 明确「全部数据」角色：仍可见全树（与菜单权限分离）。  
5. **无管辖**：非特权且 0 个有效管辖根 → 空树 + 空列表，并提示「未配置管辖部门」。

管辖根：管理部、品保部 → 树根可为这两个节点（或其共同祖先若产品要求「仍显示路径」——见 §5.3）。

---

## 4. 方案选型

| 方案 | 做法 | 优点 | 风险 |
|------|------|------|------|
| **A 快修** | HR 过滤读 `ExtOrg`∪主 `OrgId` → `SysOrg.Code` → `cc_code`，再 `cc_level` 前缀 | 改动小、账号 UI 不动 | 依赖 SysOrg↔cc 对齐；与 01 设计「零关联 SysOrg」冲突；框架 DataScope 展开 Id 不适合大树 |
| **B 正道（推荐目标）** | 落地 `Usercc`；账号「管辖」改为人事部门（或双写）；HR 一律 Usercc | 与设计稿一致、调动安全、可扩到审批/导入等 | 账号页/选部门组件要改；需迁移 ExtOrg |
| **C 过渡** | 保存 ExtOrg 时按 `Code` **同步 Usercc**；读侧只认 Usercc | 读路径干净，写入兼容现状 | 双写一致性；Code 对不齐时同步失败要提示 |

**建议推进**：先 **C（短期可验）**，验收通过后收敛到 **B（账号页直接维护 Usercc，弱化 ExtOrg 作为人事管辖源）**。A 仅作紧急补丁，不建议长期保留两套语义。

---

## 5. 改造设计（按推荐路径 C→B）

### 5.1 数据

- 建表 `Usercc`（字段与索引见 `01-user-cc-scope.md` §3）。  
- SQL 按日归档：`doc/sql/{yyyy-MM-dd}/`。  
- 一次性迁移：对现有 `SysUserExtOrg` + 用户主机构，用 `SysOrg.Code` 匹配 `cc_mstr.cc_code`，能匹配的写入 `Usercc(IncludeChild=1)`；匹配失败列入巡检清单。

### 5.2 公共解析（后端必抽）

新建如 `HrUserCcScopeService`（禁止各模块抄前缀逻辑）：

| 方法 | 用途 |
|------|------|
| `GetEffectiveRootsAsync(userId)` | Usercc JOIN 当前 `cc_mstr` → `{ CcCode, CcLevel, IncludeChild }` |
| `ApplyOrgScope(query)` | 给 `cc_mstr` 查询加 EXISTS/OR 前缀条件 |
| `ApplyEmpScope(query)` | 员工 `cc_code` → 部门 level 再套同一套 |
| `EnsureCcInScopeAsync(ccCode)` | 写操作越权校验 |
| `IsAllScope()` | 超管或特权角色 |

缓存：只缓存授权行列表，**不**缓存展开部门 Id；组织调动后如缓存了 level 则整清（见 01 §5.2）。

### 5.3 部门树展示策略

过滤后可能得到多个不相邻根（管理部、品保部）。两种 UI：

| 策略 | 说明 | 推荐 |
|------|------|------|
| **森林根** | 树顶直接是各管辖根（无「集团」父节点） | ✅ 默认，语义清晰 |
| **保留祖先路径** | 仍显示集团→…→管辖根，但对非管辖祖先不可选或仅作路径 | 可选，易误解「能管集团」 |

人数：只 rollup **可见子树内**员工；祖先路径策略下，祖先节点人数勿显示为全公司。

### 5.4 接入点（P0）

| 接口/页面 | 改造 |
|-----------|------|
| `HrOrgService.GetList` | `ApplyOrgScope` 后再建树；无范围非特权 → `[]` |
| `HrEmpService.Page` / 导出类 | `ApplyEmpScope`；若带 `parentCcCode` 须先 `EnsureCcInScope` |
| `HrEmp` Add/Update/调部门 | `EnsureCcInScope(input.CcCode)` |
| `orgTree.vue` / 人员页 | 无逻辑大改；空树提示「未配置管辖」 |
| 员工资料导入等管辖类 | 预览/提交涉及部门的，同样套 scope（可 P1） |

### 5.5 账号管理（C→B）

**阶段 C**

- 保存用户 ExtOrg 后：同步 Usercc（Code→CcCode，默认含下级）。  
- 主 `OrgId` 是否计入人事管辖：建议 **计入**（与框架「当前所属机构」一致），产品确认后写死。

**阶段 B**

- 「管辖部门」选择器改为人事组织树（`cc_mstr`），直接读写 Usercc。  
- ExtOrg 可保留给框架其它模块，但 **人事范围以 Usercc 为准**，文档与界面注明。

### 5.6 与框架 DataScope 的边界

- **不**用 `GetUserOrgIdList` 展开后 `IN` 过滤 HR 大表。  
- Sys* 模块可继续走原 OrgId DataScope。  
- 人事模块统一 `Usercc` + `cc_level` 前缀。

## 6. 实施分期

| 期 | 内容 | 验收 |
|----|------|------|
| **P0** | DDL Usercc；Scope 服务；ExtOrg→Usercc 同步/迁移；`HrOrg.GetList` + `HrEmp.Page` 过滤；空范围提示 | `adm`（非超管）登录：树仅管理部、品保部及下级；列表不可见其它部门员工；点伪造 ccCode 无效 |
| **P1** | 写操作越权；导入/组织维护页按需接入；巡检无效管辖 | 改管辖立即生效（清缓存） |
| **P2** | 账号页改为直接维护 Usercc；压缩祖先/子孙；可选「仅本部门」 | 与 01 设计稿验收清单对齐 |

不在本期：角色级管辖并集（可二期）、排除子树、把 Usercc 挂进 SysOrg 树本身。

## 7. 多语言

- 空树/无管辖提示：UI 词条进 `Web/src/i18n/pages/hrms`（zh-CN / en / zh-TW / th / vi）。  
- 部门名称仍走现有 `cc_mstr` / 译文机制，本方案不新增业务名译文表。

---

## 8. 风险与依赖

| 风险 | 应对 |
|------|------|
| `SysOrg.Code` ≠ `cc_code` | 迁移报告 + 账号保存时校验；对不齐不得静默放行全量 |
| 超管误测 | 验收账号禁用超管；文档写明 |
| 大组织性能 | 禁止展开；EXISTS + level 前缀 + `cc_level` 索引 |
| 双写不一致 | P2 收口只读 Usercc；C 阶段保存路径单测 |

## 9. 验收清单（针对本次截图）

- [ ] 用 `adm`（确认非超管）登录  
- [ ] 账号管理仍显示管理部、品保部（或 Usercc 等价配置）  
- [ ] 人员资料左侧：**不见**整集团根下的无关部门；可见两管辖根及其子部门  
- [ ] 列表人数/行与可见树一致  
- [ ] 切换管辖后重新登录或清缓存，范围立即变化  
- [ ] 超管账号仍可见全树  

---

## 10. 建议决策（请确认后实施）

1. **目标模型**：人事管辖以 **Usercc + CcCode** 为准（采纳 01 设计）。  
2. **短期**：ExtOrg 保存同步 Usercc（方案 C），先打通人员树/列表。  
3. **树 UI**：默认 **森林根**（不显示无关的「集团」壳）。  
4. **主 OrgId**：是否默认并入人事管辖 → **建议是**。

确认后按 P0 开工（DDL + Scope + GetList/Page + 同步）。
