# 审核角色树形汇报链改造方案

> 分析日期：2026-10-24  
> 定位：在现有 `hr_wf_*` 引擎上，将审批角色改为**全局汇报树**；流程节点审批人可为**审核等级 / 指定人 / 岗位**，并均可配条件  
> 状态：**已确认**（实施计划见 `06-树形汇报链实施计划.md`）  
> 依据：业务确认（见文末会话结论）+ 对齐旧系统「审核角色体系管理」左树右表

---

## 1. 意图与成功标准

把「审批角色」从偏扁平的等级挂靠，改造成与旧系统一致的**岗位角色汇报树**：树表达上下级；流程定义仍配置有序审批节点（审批人规则 + 条件）。开单后按当事人岗位定位树节点，从**上级**起沿路径处理需走汇报链的节点并派待办。

成功时：

1. 管理员可维护**一棵全局**岗位角色树（所有流程共用）：父子 = 汇报上下级。
2. 每个岗位角色节点配置：审核等级、绑定岗位、管辖部门、排序；截图中的「审核角色」列 = **审核等级**。
3. 流程定义继续配置一串节点；节点审批人规则为 **`Level`（审核等级）/ `FixedUser`（个人）/ `Post`（岗位）** 之一，均可配 `ConditionJson`。
4. 起审：**单据当事人**岗位落入某岗位角色 → **跳过本人节点** → 得到父链至根的路径（供 `Level` 规则使用）。
5. 派单：按流程节点顺序；条件不满足 / 规则解析无人（含 Level 不在路径）→ 记日志并跳过该节点；**若全部节点均被跳过则开单/推进报错**（不允许零审批通过）。
6. 同一条汇报路径上**不允许重复同一审核等级**（保存时校验）。
7. 在途单继续旧算法；**仅新开单**走汇报路径算法；树数据由管理员上线后重建（不导入旧体系）。

---

## 2. 目标 / 非目标 / 反目标

### 2.1 目标

- `ParentId` 语义从「分类」改为**汇报上级**；提供树查询与左树右表管理页。
- 新增「按汇报路径 + 等级」解析算法，替换（或并列切换）当前「等级下所有角色 + AuditOrder 空人升级」在 `Level` 规则下的默认行为。
- 落实节点 `ConditionJson` 求值（当前运行时尚未真正跳过条件）。
- 开单上下文增加申请人岗位（由用户/员工解析），用于定起点。

### 2.2 非目标（本期不做）

| 不做 | 说明 |
|------|------|
| 多棵汇报树 / 按流程绑树 | 已确认全局一棵 |
| 流程节点绑具体汇报树 `RoleId` | 不绑树上的岗位角色 Id；用等级 / 人 / 人事岗位编码 |
| 可视化自由拖拽画布 | 仍用有序列表 + 属性 |
| 取消 FixedUser | 个人规则保留并作为一等配置项 |
| 历史在途单按新算法重算 | 在途仍吃开单时快照；新算法仅对新开单生效 |

### 2.3 反目标

- 流程不配节点、一律盲审到树根（与「节点 + 条件」冲突）。
- 仍用「等级下全库角色 + 管辖」找人，忽略汇报路径（与树改造目标冲突）。
- 申请人本人岗位角色也生成待办（已确认从父节点起审）。

## 3. 已锁定业务规则

| # | 规则 |
|---|------|
| R1 | 树 = 审批人上下级汇报链，非纯分类目录 |
| R2 | 自动语义：沿路径从下往上；**每个节点带审核等级** |
| R3 | 截图「审核角色」= 审核等级（`hr_wf_level`） |
| R4 | 起审：**单据当事人**（`SubjectEmpId` → 员工岗位）落入某岗位角色；代提时不以发起人岗位定路径 |
| R5 | **跳过本人节点**，从父节点开始 |
| R6 | 候选路径一直到**树根**（不另设「最高审到哪级」截断；实际是否审由流程节点决定） |
| R7 | 某节点条件不满足 / 路径无该等级 / 解析不到人 → **跳过**该流程节点并记日志 |
| R7b | **全部流程节点均被跳过 → 报错**（禁止零人审批通过） |
| R8 | **一棵全局树**，所有流程共用 |
| R9 | 流程定义仍配一串节点，且**每节点可设条件** |
| R10 | 节点审批人规则三选一：**审核等级 `Level`** / **个人 `FixedUser`** / **岗位 `Post`**（均非汇报树 `RoleId`）；均可配条件 |
| R11 | 同一汇报路径上同一 `LevelId` 不得重复 |
| R12 | **在途单**按原 Level+AuditOrder 逻辑；**新开单**走汇报路径 |
| R13 | 树数据**不导入**旧体系，上线后由管理员重建 |

建造方补充（可改）：

| # | 默认 | 说明 |
|---|------|------|
| B1 | 多岗位命中多个角色 | 取**树深最大**（最靠近叶子）的那一个；若深度相同则报错要求改配置 |
| B2 | 当事人无岗位 / 岗位未挂任何角色 | 开单失败（明确错误码），不静默空跑 |
| B3 | 命中角色无父节点（当事人已是根） | 无上级路径 → 开单失败（与 R7b 一致，不出现零审批通过） |
| B4 | 条件语法 | 沿用既有 `ConditionJson` 契约（见 `03-表字段与接口契约.md`）；本期必须在 `DispatchFromAsync` 中求值 |
| B5 | 双轨切换 | 开单时写入解析模式到实例/快照（如 `AssigneeResolveMode=LegacyLevel|ReportPath`）；在途读快照走旧逻辑，新开写 `ReportPath` |
| B6 | 与旧 `AuditOrder` 升级 | 仅 `LegacyLevel` 仍升级；`ReportPath` 下空人只跳过本流程节点。超时升级（P2）另议 |
| B7 | 职能等级 `IsFunctional` | 仍可被流程节点显式选中；不参与「路径外自动插入」 |
| B8 | `Post` 找人 | `postId` → 在岗 `HrEmployee` → `SysUser.JobNum`；**不**要求落在汇报路径上；一岗多人按节点 `NodeMode`（默认或签）；空人跳过 |
| B9 | `FixedUser` | 指定用户 Id 列表；与路径无关；用户无效/停用则剔除，全空则跳过 |

### 3.1 节点审批人规则（R10 展开）

| type | 配置 | 是否依赖汇报路径 | 解析 |
|------|------|------------------|------|
| `Level` | `levelId` | **是**（ReportPath）/ Legacy 仍旧等级扫描 | 路径上唯一匹配该等级的岗位角色 → 管辖 + 绑定岗位 → 用户 |
| `FixedUser` | `userIds[]` | 否 | 直接指定用户 |
| `Post` | `postId`（人事岗位编码，同 `HrEmployee.PostId`） | 否 | 该岗位在岗员工 → 用户 |

> 仍**不**支持流程节点直接绑汇报树上的某个 `hr_wf_role.Id`；需要「某条支路的某一环」时，用该环上的**审核等级**（路径命中）表达。

## 4. 概念模型

```text
全局岗位角色树 (hr_wf_role.ParentId = 上级)
  节点属性：Name、LevelId（审核等级）、Posts、Scopes、OrderNo
        │
        ▼ 开单：单据当事人 Post → 命中节点 S → 路径 Path = Ancestors(S) 不含 S，至根
        │
流程定义节点序列 (hr_wf_def_node)
  每节点：AssigneeRule(Level|FixedUser|Post) + ConditionJson + NodeMode
        │
        ▼ 按 OrderNo：条件？→ 按规则解析人？→ 派待办 / 跳过
              Level：须在 Path 上命中等级对应角色
              FixedUser / Post：与 Path 无关
```

与一期文档差异（覆盖 `01-方案设计.md` §5.1 中「ParentId 仅分类、不作升级链」）：

| 原约定 | 新约定 |
|--------|--------|
| `ParentId` 可选分类 | `ParentId` = 汇报上级，全局一棵树 |
| `Level`：等级下所有角色 + 管辖 + AuditOrder 空人升级 | `Level`：仅路径上等级对应的**唯一**角色 + 管辖仍校验 + 空人跳过节点 |
| 流程节点主要选等级 | 节点可选 **等级 / 个人 / 岗位**；仅 `Level` 依赖汇报路径 |

管辖部门：**保留**（对 `Level`）。路径定角色后，仍要求该角色管辖覆盖 `SubjectCcCode`；不覆盖则视为无人 → 跳过（记 `SkipEmpty` 或新动作 `SkipScope`）。`Post` / `FixedUser` 本期不做管辖过滤（B8/B9）。

## 5. 数据模型变更

### 5.1 表结构：基本可复用

| 表 | 变更 |
|----|------|
| `hr_wf_role` | **无强制加列**；明确 `parent_id` 语义为上级；建议根节点 `parent_id IS NULL`；可选增加虚拟根「审核流程」仅 UI，或真实根角色 |
| `hr_wf_level` | 不变 |
| `hr_wf_role_post` / `hr_wf_role_scope` | 不变 |
| `hr_wf_def_node` | 表结构不变；`assignee_rule_json` 支持三种形状（见下）；`condition_json` 必用 |
| 实例快照 | 建议在 `DefNodesSnapshot` 增加 `AssigneeResolveMode`、可选 `ReportPathRoleIds`；非必须落库新列 |

`AssigneeRuleJson` 形状：

```json
{ "type": "Level", "levelId": 10001 }
{ "type": "FixedUser", "userIds": [20001, 20002] }
{ "type": "Post", "postId": "P_FIN_CLERK" }
```

常量：现有 `HrWfConsts.RuleLevel` / `RuleFixedUser`；新增 `RulePost = "Post"`。DTO `HrWfAssigneeRule` 增加 `string? PostId`。

### 5.2 校验（保存岗位角色时）

1. 禁止把节点挂到自己的子孙下（防环）。
2. 从该节点沿父链到根，收集 `LevelId`，**不可出现重复**（含自身）。
3. 移动父级时对「被移动子树 + 新路径」重算校验。
4. 同一 `post_id` 允许挂多个角色，但开单按 B1 消歧。

### 5.3 接口增量（建议）

| API | 说明 |
|-----|------|
| `hrWfRole/Tree` | 返回整棵树（或按父懒加载） |
| `hrWfRole/Page` | 保留；支持 `parentId` 过滤（右表：当前节点的**直接子节点**列表，对齐截图） |
| `hrWfRole/Save` | 增加环与路径等级唯一校验 |
| `hrWfRole/Move` | 可选：改父 + 排序 |
| 运行时 | `Start` 解析当事人岗位并建路径；`Dispatch` 条件 + Level/FixedUser/Post 解析 |

截图右表列映射：

| 列 | 字段 |
|----|------|
| 岗位角色名称 | `hr_wf_role.name` |
| 审核角色（实为等级） | `level_id` → `hr_wf_level.name` |
| 管辖部门 | `hr_wf_role_scope` |
| 排序 | `order_no` |

左树选中节点 A 时：右表展示 **A 的子节点**（不是 A 自身一行）；编辑子节点的等级/管辖/岗位。

## 6. 运行时算法

### 6.1 构建汇报路径

```text
输入：subjectEmpId（必填）、subjectCcCode
1. 由 SubjectEmpId 取员工岗位 postId（失败 → 开单失败）
2. roles = 启用中且绑定了该 postId 的 hr_wf_role
3. 按 B1 选定 startRole
4. 若 startRole.ParentId 为空 → B3 开单失败
5. path = []；cur = Parent(startRole)；while cur != null：path.Add(cur)；cur = Parent(cur)
6. 校验 path 上 LevelId 唯一（数据应已保证；运行时再断言）
输出：path（从近到远，父 → … → 根）
```

> 发起人 `ApplicantUserId` 仅作操作者/权限，**不定路径**。代提时路径始终跟当事人。

### 6.2 按流程节点派单（替换/增强现 `DispatchFromAsync`）

对 `nodes[startIndex..]` 每个启用节点：

1. 若 `ConditionJson` 存在且对当前 `FormData` 为假 → 跳过（记日志 `SkipCondition`）。
2. 解析 `AssigneeRule`：
   - `FixedUser`：按 `userIds` 取有效用户；空 → 跳过（`SkipEmpty`）。与路径无关。
   - `Post`：按 `postId` 解析在岗员工→用户（B8）；空 → 跳过。与路径无关。
   - `Level` + `ReportPath`：在 `path` 中找 `LevelId == rule.LevelId` 的角色 `R`；找不到 → 跳过（`SkipNotOnPath`）；用 **仅角色 R** + 管辖 + 岗位 → 用户；空 → 跳过（`SkipEmpty`）。
   - `Level` + `LegacyLevel`：沿用现 `ResolveByLevelAsync`（含 AuditOrder 升级）。
   - `DeptManager` / `Reporter`：仍按原计划预留，与树无关；未实现则空→跳过。
3. 有人则按 `NodeMode`（Or/And/Serial）建待办并返回；无人则 continue。
4. **本轮从 startIndex 起若从未成功派过任何待办且已无后续节点**：
   - 若处于开单后首次 Dispatch 且零节点命中 → **报错回滚/失败**（R7b），不得 `Approved`。
   - 若审批中同意后后续全跳过 → 同样 **不得静默通过**；报错或挂起（建造方默认：**实例置为失败态并记日志**，与 R7b 一致）。

### 6.3 与「审到树根」的关系

- **路径**覆盖到树根（R6）。
- **是否产生待办**完全由流程节点列表 + 条件决定：未配置的等级不会自动插入；配置了但条件假或路径无该等级则跳过。
- 因此「审到树根」= 路径足够长；不是「无视流程节点强制每一环都审」。

## 7. 前端方案（对齐截图）

### 7.1 审核角色体系管理页（改造现有角色页或新建）

```text
┌─────────────┬──────────────────────────────────────────┐
│ 全局汇报树   │  子节点表格（岗位角色 / 等级 / 管辖 / 排序） │
│ 可增删改拖拽 │  工具栏：新增子角色、异常角色、调整（二期）   │
└─────────────┴──────────────────────────────────────────┘
```

- 左树：`el-tree` / 项目既有树组件；根下为各顶级岗位角色（如总经理）。
- 右表：服务端排序（`orderNo`）；列头可排序（遵守页面排序规范）。
- 编辑抽屉：名称、编码、审核等级、岗位多选、管辖部门、启用。

### 7.2 流程定义节点编辑

- 审批人规则类型三选一：**审核等级** / **指定人** / **岗位**（对应 `Level` / `FixedUser` / `Post`）。
- 选等级：下拉 `hr_wf_level`；帮助文案：「仅当单据当事人汇报路径上存在该等级时才会审批」。
- 选个人：用户多选。
- 选岗位：人事岗位编码多选或单选（本期 **单 `postId`**，与 B8 一致；若要多岗位可后续扩展为数组）。
- 条件：表单字段表达式（沿用契约 / 本期求值器）。

## 10. 测试要点

1. 当事人岗位命中叶子 → 第一待办为父节点等级对应人；代提时路径不跟发起人。
2. 流程节点等级不在路径上 → 跳过；若因此导致零待办 → 报错。
3. 条件为假 → 跳过；为真且在路径 → 派单。
4. 路径角色管辖不覆盖 → 跳过。
5. 全部节点跳过 → 开单/推进失败，不得 Approved。
6. 保存导致路径同等级重复 → 拒绝。
7. 成环挂接 → 拒绝。
8. 当事人已是根 → 开单失败（B3）。
9. `FixedUser` / `Post` 节点不受汇报路径影响；`Level` 受路径约束。
10. 在途 Legacy 实例仍可 AuditOrder 升级；新单 Level 不升级。

## 11. 会话结论摘要

- 树 = 汇报链；等级挂在岗位角色上；截图「审核角色」= 等级。
- 起审按**单据当事人**岗位；跳过本人；路径到根；单节点可跳过，**全跳过报错**。
- 全局一棵树；流程仍配节点且可设条件；节点审批人 = **等级 / 个人 / 岗位**。
- 路径上同等级不重复。
- 在途旧逻辑、新开新逻辑；树由管理员重建、不导入。
